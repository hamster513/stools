# Security Tools (STools)

Рабочее место сотрудника ИБ: набор модулей, каждый анализирует одну
систему и указывает на проблемные области. Продукт один — вход, сессия
и оболочка общие; модули подключаются к платформе.

| Модуль | Что анализирует | Состояние |
|---|---|---|
| **ATT&CK** | сводная матрица техник: покрытие правилами SIEM и экспозиция из VM и AD слоями на одной матрице, разрывы, цепочки кампаний | работает |
| **SIEM Rules Analyzer** | база знаний MaxPatrol SIEM: средовые значения в правилах, клоны, табличные списки, разметка правил по ATT&CK | работает |
| **Антивирус** | Kaspersky Security Center: покрытие относительно AD, устройства без агента и защиты, компоненты, базы, политики и задачи, аудит сервера (2FA, администраторы, сертификат); сбор скриптом или по Open API | работает |
| **Active Directory** | 22 проверки домена: DCSync, привилегированные группы, делегация, Kerberoast, ACL, AD CS; сбор скриптом или по LDAP | работает |
| **Vulnerability Management** | хосты и CVE из MaxPatrol VM, обогащение EPSS/NVD/ExploitDB/Metasploit, риск по формуле | работает |
| **Assets** | реестр хостов из VM, антивируса, AD, сканера сети и DNS: где актив засветился, какие данные устарели, кого никто не описал; сети с зонами, скан и DNS по расписанию | работает |
| Сетевой периметр | правила межсетевых экранов и открытые сервисы | в разработке |

## Модуль ATT&CK

Сводная матрица техник: одна картина по всем модулям. Модуль владеет базой
знаний (бандл MITRE, русские переводы, распространённость, кампании,
применяемость техник в России), а данные о своей области ему отдаёт каждый
модуль сам — своим **слоем**: SIEM даёт покрытие правилами, VM — хосты с
уязвимостями выше порога риска, AD — незакрытые находки доменов. Техника
без покрытия, у которой есть экспозиция, — разрыв: её нечем увидеть, и в
инфраструктуре есть чем её выполнить. Те же разрывы накладываются на
цепочки реальных кампаний.

Новый модуль добавляет свой слой одной регистрацией в `__init__.py`;
матрицу и фронт править не нужно — счётчик незнакомого слоя матрица
показывает нейтральным тоном, свой цвет ему заводят по желанию. Контракт
API и контракт слоя — `docs/attack/api.md`.

## Модуль SIEM Rules Analyzer

Принимает выгрузку базы знаний MaxPatrol SIEM и отвечает на три вопроса:
где в правилах зашиты средовые значения, которым место в табличных
списках; где логика продублирована; какие табличные списки стали точками
отказа. Схема именования выводится из данных выгрузки, критичность
списков — из числа зависящих правил. Вендорских имён в коде нет.

На эталонной выгрузке из 187 правил:

- **1093 находки** средовых значений, зашитых в тела правил, по пяти
  классам тяжести и по полярности;
- **488 расхождений** «правило ↔ табличный список»;
- **16 пар клонов** — форки одной логики с разошедшимися whitelist'ами;
- **список, который читают 72 правила и которого нет в выгрузке вовсе.**

## Модуль Vulnerability Management

Импортирует хосты и их CVE из MaxPatrol VM (по API или из CSV-экспорта),
обогащает шестью справочниками (EPSS, NVD, Exploit-DB, Metasploit, CTID
ATT&CK, CISA KEV) и считает риск каждой пары хост–CVE:

```
Risk = 100 × L × S × V
```

L — вероятность эксплуатации (1, если CVE в CISA KEV; иначе EPSS, эксплойты
Exploit-DB и модули Metasploit объединяются как независимые вероятности),
S — тяжесть (CVSS ÷ 10 с поправкой на достижимость по вектору атаки и доступу
хоста из интернета), V — ценность хоста (критичность плюс надбавки зоны за
интернет и конфиденциальные данные). Веса и пороги уровней задаются в
настройках; L хранится у CVE, V у хоста, пары пересчитываются одним запросом.
Справочники для сетей без интернета собирают в один архив скрипты
`frontend/public/vm/download-references.{ps1,sh}`, архив загружается в
настройках одним файлом. Контракт API — `docs/vm/api.md`.

## Модуль Active Directory

Двадцать две проверки AD Security Scanner (DCSync, теневые администраторы,
делегация, RBCD, Kerberoast и AS-REP, ACL на OU и GPO, AD CS — шаблоны,
центр сертификации и привязка сертификатов — и другие) над выгрузкой
домена. Выгрузку даёт PowerShell-скрипт на доменной машине
(`docs/ad/collector.md`) или сам модуль по LDAP/SMB из контейнера;
формат один, проверки одни. Снапшоты сравниваются между собой, находки
можно принять как норму. Контракт API — `docs/ad/api.md`.

## Модуль Антивирус

Двадцать девять проверок состояния защиты Kaspersky Security Center:
покрытие устройств (`COVER_AD_MISSING`, `COVER_KSC_ONLY`, `UNASSIGNED`,
`NO_AGENT`), состояние защиты (`NO_PROTECTION`, `RTP_OFF`, `COMPONENT_OFF`,
`HOST_CRITICAL`, `REBOOT_PENDING`), базы и поиск (`BASES_OLD`,
`THREATS_ACTIVE`, `NO_FULLSCAN`, `AGENT_SILENT`), версии
(`PRODUCT_OUTDATED`), политики и задачи групп (`POLICY_NONE`,
`POLICY_INHERIT_BROKEN`, `TASK_NO_UPDATE`, `TASK_NO_SCAN`, `TASK_FAILED`,
`TASK_STALE`), лицензия (`LICENSE`).

Содержимое политик продуктов защиты собирается отдельно и проверяется на
замки (`POLICY_NO_LOCKS`, `POLICY_WEAK_LOCKS`, `POLICY_CONTENT_MISSING`) —
экран «Политики и задачи» показывает долю замкнутых настроек каждой
политики и ссылку на её содержимое с деревом секций.

Отдельный блок проверок — аудит самого сервера KSC, не хостов: обязательна
ли двухэтапная проверка для входа в консоль (`KSC_2FA_OFF`), не держит ли
внутренняя (не доменная) учётка KSC административную роль
(`KSC_INTERNAL_ADMIN`, справочно все держатели ролей — `KSC_ADMINS`), не
истекает ли сертификат сервера (`SERVER_CERT`), не молчит ли подчинённый
сервер иерархии (`SECONDARY_SERVER_STALE`). Экран «Сервер KSC» показывает
эти находки вместе с администраторами, внутренними учётками, сертификатами,
подчинёнными серверами и точками распространения обновлений.

Выгрузку даёт PowerShell-скрипт на машине внутри сети
(`docs/ksc/collector.md`) или сам модуль онлайн по Open API KSC (порт
13299, учётная запись KSC с правом чтения — внутренняя или доменная).
Формат один, проверки одни. Покрытие сверяется и внутри KSC, и относительно
AD: нужен снапшот домена в модуле AD, пересчёт снапшота KSC подхватывает
актуальный на момент пересчёта снапшот AD. Выгрузки хранятся в `data/ksc/`
(лимит на приём — 200 МБ). Контракт API — `docs/ksc/api.md`.

## Модуль Assets

Один реестр хостов поверх модулей: актив и наблюдения источников — VM,
антивируса, AD, сканера сети и DNS. Каноническая карточка берётся из самого
свежего наблюдения, поэтому видно, какой источник отстал (в DHCP-сетях IP
меняется, а VM и антивирус показывают старый), у какого хоста нет агента
антивируса, какой компьютер AD давно неактивен и какие хосты в сети никто не
описал. Расхождения — находки на общих статусах: их берут в работу,
назначают, принимают риск; принятый риск и ложное срабатывание убирают
расхождение из счётчиков, карточка показывает его со статусом. Сети
описываются с зоной и площадкой; сканер (ICMP и TCP из контейнера API) и
обновление через DNS (прямые и обратные запросы, чтение зон AD) запускаются
вручную или по расписанию планировщика платформы. У хостов антивируса и VM —
ссылка «в Assets». Как пользоваться и лестница первого скана —
`docs/assets/overview.md`, контракт API — `docs/assets/api.md`.

## Запуск

```bash
cp ops/.env.example ops/.env
# заполните POSTGRES_PASSWORD и STOOLS_SESSION_SECRET
docker compose -f ops/docker-compose.yml up --build
```

По умолчанию сессионная cookie требует TLS (`STOOLS_SESSION_COOKIE_SECURE=true`
в `ops/.env.example`). Два варианта:

- **С TLS** — задайте `STOOLS_SITE_ADDRESS` в `ops/.env` (имя хоста, например
  `stools.example.ru`): Caddy сам получит сертификат и включит HTTPS
  (`ops/Caddyfile`). Порт 443 нужно опубликовать дополнительно — по
  умолчанию стек публикует только `STOOLS_PORT`/80.
- **Лаборатория по HTTP** — оставьте `STOOLS_SITE_ADDRESS` пустым и явно
  поставьте `STOOLS_SESSION_COOKIE_SECURE=false`; иначе Safari выбрасывает
  cookie по HTTP, и вход молча не срабатывает.

Интерфейс — `http://localhost:8080`. Первый пользователь заводится
вручную, регистрации в интерфейсе нет:

```bash
docker compose -f ops/docker-compose.yml exec api python -m api.cli create-user <логин>
```

Пароль спрашивается интерактивно и в историю оболочки не попадает.

## Роли, группы и общие настройки

Права — уровни по областям, одна проверка на всё приложение (`api/rbac.py`).
Области — модули и платформа (`/settings`), уровни — запрет, **аудитор**
(чтение), **аналитик** (запись в модуле: разметка, статусы находок) и
**администратор** (сверх того настройка модуля — подключения, расписания,
справочники; в платформе — учётки, группы, роли, журнал, OIDC). Роль — набор
уровней по областям; роль назначается группе, пользователь получает права
через свои группы (в каждой области — максимум по ним). Встроенные роли
«Администратор», «Аналитик», «Аудитор» и группы «Администраторы»,
«Аналитики», «Аудиторы» заводятся при первом запуске; свои роли и группы —
в `/settings` → «Доступ» (вкладки «Роли» и «Группы»). Исключение — состояние модели LLM
(`/api/settings/llm`), матрицы ATT&CK (`/api/settings/attack`) и настройки
статусов находок (`/settings/findings`, `/api/settings/findings`): их читают
сами страницы модулей, поэтому эти чтения открыты всем; меняют их администратор
платформы (матрицу ATT&CK — администратор модуля ATT&CK).
Первый пользователь, заведённый через `create-user`, попадает в группу
«Администраторы» автоматически; каждый следующий — в «Аналитики», если
группы не указаны явно `--group <имя>` (ключ повторяется). Уровни, правила
проверки, самоблокировка и миграция — `docs/platform/access.md`.

После `alembic upgrade head` существующие учётки попадают в группы по
прежней роли: `admin` — «Администраторы», `analyst` — «Аналитики»,
`auditor` — «Аудиторы». Прежние аналитики настройку модулей теряют: вернуть
её можно отдельной ролью с уровнем «Администратор» в нужном модуле.

Закладка на `/settings` теперь открывает общие настройки платформы —
настройки модуля SIEM переехали на `/settings/siem`.

Журнал действий пишет адрес клиента из заголовка `X-Forwarded-For`,
который проставляет Caddy, поэтому API должен быть доступен только через
Caddy: порт 8000 наружу не публикуется (`ops/docker-compose.yml`), и
подделать адрес в журнале заголовком неоткуда.

В `/settings` — настройки; шестерёнка в шапке открывает их любому вошедшему: сводка «Данные»
и профиль доступны всем, страница модуля — с уровня «Аналитик» в нём (настройку внутри неё
меняет «Администратор» модуля), а разделы платформы — с уровня «Чтение» платформы:

- **Доступ** (`/settings/access`) — четыре вкладки: **Пользователи** (создание,
  группы, блокировка, сброс пароля), **Группы** и **Роли** (уровни доступа по
  модулям и кто их получает), **Вход** (пароли и сессии: срок сессии, таймаут
  бездействия, срок хранения журнала действий; вход по OIDC, см. ниже);
- **Журнал действий** — кто, что и когда сделал, с фильтрами и выгрузкой
  в CSV;
- **Модель LLM** — адрес и модель для разметки ATT&CK и перевода техник,
  общая для всей платформы;
- **Данные** — сводка свежести баз и выгрузок всех модулей (когда обновлялось,
  свежо ли, откуда) со ссылкой на нужную секцию;
- **Модули** — настройки каждого модуля на `/settings/<модуль>`: подключения,
  расписания, загрузки выгрузок и справочников; база ATT&CK (версия матрицы,
  обновление файлом или онлайн) и применяемость техник в России — на
  `/settings/attack`;
- **Статусы находок** — какие статусы учитывать в подсчётах, предельный срок
  и право принятия риска; раздел видят все, меняет администратор платформы.

Контракт ручек — `docs/api-contract.md` («Общие правила», «Общие
настройки»).

## Статусы находок

У находок AD, Антивируса, SIEM, VM и Assets (расхождения активов) один жизненный цикл: «Новая», «В
работе», «Принят риск», «Ложное срабатывание», «Исправлено» ставят люди,
«Устранена» и «Переоткрыта» — система по свежим данным. У находки есть
исполнитель, срок, срок действия принятого риска и история. Списки по
умолчанию показывают открытые; «Мои находки» (значок в рейке) собирают
назначенное мне из всех модулей; принятый риск с истёкшим сроком раз в сутки
снова становится новой находкой, а если находки уже нет в данных — устранённой. Какие статусы учитывать в подсчётах —
«Настройки → Статусы находок». Подробно: `docs/platform/findings.md`.

## Вход через Avanpost FAM

Кроме входа по паролю, STools умеет входить через провайдера OpenID
Connect — Avanpost FAM или любой другой с тем же протоколом. Включается
в `/settings` → «Доступ» → «Вход» (блок «Вход по OIDC»): администратор указывает адрес
STools, адрес провайдера (`issuer_url`), `client_id`, `client_secret` и
список scope. Права вошедшим дают группы из OIDC — они заводятся в
`/settings` → «Доступ» → «Группы»; включить вход можно, только когда есть хотя бы одна.

В FAM для STools нужно завести клиента (Authorization Code + PKCE)
и указать:

- **redirect URI** — показан прямо в настройках STools (`redirect_uri`),
  меняется вместе с адресом STools;
- **scope** — как минимум `openid profile email` плюс тот, что отдаёт
  claim со списком групп пользователя;
- имя claim'а с группами — совпадает с тем, что указано в настройках
  STools (`groups_claim`, по умолчанию `groups`). Группы принимаются
  строками или объектами, как их отдаёт Avanpost FAM
  (`{"id": …, "name": …}`): в группе из OIDC («имя в OIDC») можно указать
  и имя группы, и её идентификатор.

Членство в группах из OIDC пересчитывается при каждом входе: значения
claim'а точно сравниваются с «именем в OIDC» групп, совпавшие группы
пользователь получает, прочие теряет; группы без совпадения игнорируются.
Права из нескольких групп складываются — в каждом модуле **побеждает
самый широкий уровень**. Локальные группы, назначенные такой учётке в
STools, вход не трогает. Если после пересчёта у человека нет ни одной
группы, во входе отказано, и новая учётка для него не заводится. Пересчёт
не держит последнего администратора: убрали группу в каталоге — человек
больше не администратор; выход — завести нового локального администратора
`create-user <логин> --group Администраторы` на сервере (существующему
логину команда права не возвращает).

Первый администратор STools — всегда локальная учётка, заведённая
`create-user` (см. выше): до того, как OIDC настроен и включён, попасть
в `/settings` можно только под локальной учёткой. Учётки, заведённые
через провайдера, пароля не имеют вовсе — входят только через него;
сброс и смена пароля для них недоступны.

Доступ-лог uvicorn в образе API выключен (`--no-access-log`): в строке
запроса на `/api/auth/oidc/callback` приходит код авторизации, и попадать
в логи контейнера ему незачем — что сделано, видно в журнале действий.

Начатый вход привязан к браузеру отдельной cookie (`stools_oidc_state`):
если вернуться по ссылке от провайдера в другом браузере или вкладке —
вход будет отклонён. Доводить его до конца нужно в том же браузере, где
он был начат.

Контракт ручек — `docs/api-contract.md` («Аутентификация», «Общие
настройки»).

## Работа без сети

После сборки образов стек не обращается наружу сам по себе: шрифты собраны
в образ, модели и справочники лежат локально. Исключения — только по
действию или настройке (см. «Исходящий трафик» ниже) и `STOOLS_TLS=auto`
с именем хоста, при котором Caddy ходит за сертификатом в ACME. Проверить можно так:

```bash
docker network disconnect stools_default stools-api-1
docker compose -f ops/docker-compose.yml restart api
```

```
frontend/src/platform/       оболочка: рейка модулей, заглушки
frontend/src/modules/siem/   экраны модуля SIEM (/siem/…)
frontend/src/modules/vm/     экраны модуля VM (/vm/…)
frontend/src/modules/ad/     экраны модуля AD (/ad/…)
```

Ядро модуля SIEM доступно из командной строки — удобно в CI и при
доработке парсеров:

```bash
cd backend
python3 -m venv .venv && ./.venv/bin/pip install -e ".[dev]"

./.venv/bin/kbaudit stats "../выгрузка.zip"
./.venv/bin/kbaudit profile "../выгрузка.zip" --write
./.venv/bin/kbaudit findings "../выгрузка.zip" --kind 1
./.venv/bin/kbaudit divergence "../выгрузка.zip"
```

Значения находок — адреса, имена хостов, учётные записи. По умолчанию они
скрыты; чтобы увидеть, нужен явный `--show-values`.

## Безопасность

Продукт хранит выгрузки целиком, то есть внутри оказывается инвентарь
внутренней инфраструктуры. Модель доступа к сервису должна быть не слабее,
чем к анализируемым системам.

- Все ручки API, кроме входа, закрыты сессией — на уровне монтирования
  роутеров, а не по списку.
- Значения находок не отдаются в списках — только по явному запросу.
- Выгрузки, продукты разбора и файл `ops/.env` исключены из git.
- Пароли подключений AD, KSC, MaxPatrol VM и секрет клиента OIDC лежат в
  базе зашифрованными (Fernet, ключ выводится из `STOOLS_SESSION_SECRET`),
  токены сессий — HMAC-SHA256 с ключом из того же секрета. Сохранённые до
  шифрования пароли шифруются при следующем сохранении подключения или
  настроек; сразу после обновления рекомендуется зашифровать их все
  командой `docker compose -f ops/docker-compose.yml exec api python -m
  api.cli reseal-secrets` (печатает только число перешифрованных секретов
  по видам). Без
  `STOOLS_SESSION_SECRET` сервис с `STOOLS_SESSION_COOKIE_SECURE=true` не
  стартует. **Смена `STOOLS_SESSION_SECRET` завершает все сессии и делает
  сохранённые секреты нечитаемыми — их нужно ввести заново** (проверка
  подключения ответит «секрет зашифрован другим ключом — введите его
  заново»).
- **Ротация `STOOLS_SESSION_SECRET`.** Ломаются все сессии: хеш токена
  зависит от ключа, и вход нужен заново. Кроме того, перестают читаться
  все уже зашифрованные секреты. Второго ключа для расшифровки нет, а
  `reseal-secrets` шифрует только открытые значения и зашифрованные не
  трогает. Поэтому порядок такой:
  1. Сменить ключ **до** первого шифрования, то есть до `reseal-secrets` и
     до первого сохранения подключений новой версией. Тогда открытые секреты
     сразу шифруются новым ключом, и вводить ничего не нужно.
  2. Если секреты уже зашифрованы старым ключом, после смены ключа каждый
     секрет вводится заново в своей форме: подключения AD и KSC, настройки
     VM, OIDC. `reseal-secrets` после ротации этого не исправит.

  Ключ читается из окружения при создании контейнера. Поэтому после правки
  `ops/.env` нужен `docker compose … up -d api`, `docker restart` не хватит.
- Cookie сессии по умолчанию Secure (см. «Запуск» про `STOOLS_SITE_ADDRESS`
  и `STOOLS_SESSION_COOKIE_SECURE`); Caddy добавляет `Strict-Transport-Security`
  (`max-age=31536000`, только когда соединение https) и `Content-Security-Policy`
  (`default-src 'self'`, `script-src 'self'`, `style-src` — с `'unsafe-inline'`
  под инлайновые `style={{...}}` React, `frame-ancestors 'none'`) — `ops/Caddyfile`.
- **TLS.** Без TLS cookie по HTTP не работает (`STOOLS_SESSION_COOKIE_SECURE=true`
  по умолчанию). В `STOOLS_SITE_ADDRESS` указывается имя хоста или IP, порт
  443 нужно опубликовать. Откуда сертификат, задаёт `STOOLS_TLS` (`ops/Caddyfile`):
  - `auto` (по умолчанию) — Caddy сам получает сертификат по ACME. Нужен
    выход в интернет к удостоверяющему центру и публичное имя.
  - `internal` — без сети: свой удостоверяющий центр Caddy (`tls internal`).
    Корневой сертификат лежит в контейнере web в
    `/data/caddy/pki/authorities/local/root.crt` (том `caddy-data`, переживает
    пересоздание). Его нужно раздать в доверенные корни рабочих мест
    (например, групповой политикой): `docker compose -f ops/docker-compose.yml
    cp web:/data/caddy/pki/authorities/local/root.crt .`.
  - `files` — свой сертификат из внутреннего УЦ (`tls cert.pem key.pem`):
    положить `ops/tls/cert.pem` (с цепочкой) и `ops/tls/key.pem`. Каталог
    монтируется в `/etc/caddy/tls` и в git не попадает.

  Либо свой терминатор перед Caddy. Адрес клиента для журнала и троттлинга
  API берёт из `X-Forwarded-For`, а Caddy перезаписывает этот заголовок
  адресом того, кто к нему подключился (`header_up X-Forwarded-For {client_ip}`),
  так что подставить свой адрес клиент не может. Если перед Caddy стоит
  ещё один прокси, этим адресом будет адрес прокси, один на всех. Тогда
  счётчик неудачных входов по IP общий для всех пользователей, пока в Caddy
  не настроен `trusted_proxies`.
- **Лимиты тела запроса** (`backend/api/limits.py`). Лимит проверяется до
  маршрутизации и до проверки сессии. `Content-Length` больше лимита сразу
  получает 413, тело без длины обрывается на лимите. По умолчанию лимит
  2 МБ. Свои лимиты — только у ручек загрузки файлов, по методу и пути
  целиком: выгрузки SIEM — 300 МБ, импорт файлом и загрузка справочников
  VM — 500 МБ, файлы выгрузок AD и KSC — 200 МБ, бандл ATT&CK — 100 МБ,
  ru-ttp — 20 МБ, эталонная разметка ATT&CK — 50 МБ. JSON-ручки рядом с
  ними получают 2 МБ. Запрос с лимитом выше 2 МБ пропускается только с
  живой сессией, иначе 401 до чтения тела. Caddy пропускает на `/api/*` тело
  не больше 600 МБ.
- **Распаковка** (`backend/kbaudit/safe_io.py`). Сжатые выгрузки AD и KSC
  распаковываются не больше чем в 512 МБ. Член zip-архива (в том числе
  xlsx) ограничен 512 МБ, сумма членов — 2048 МБ. Проверяются и заголовки
  архива, и фактически прочитанные байты. Потолки ограничивают память, но
  не гарантируют её: разбор JSON занимает кратно больше самих байтов, и
  вошедший пользователь с правом загрузки может исчерпать `mem_limit`
  контейнера API (`STOOLS_API_MEM`, по умолчанию 6 ГБ) специально подобранным файлом; после падения
  контейнер перезапускается.
- **Ответы внешних систем.** Ответы KSC Open API и MaxPatrol VM читаются в
  память не больше 64 МБ. Ленты VM (NVD, EPSS, ExploitDB) скачиваются на
  диск не больше 512 МБ, бандл ATT&CK — не больше 120 МБ.
- **Троттлинг входа** (`backend/api/routers/auth.py`). Неудачные входы за
  скользящие 15 минут считаются по журналу отдельно по логину и по IP. С
  10 неудач по логину или 50 с одного IP вход отвечает 429 с
  `Retry-After: 900`, даже при верном пароле. Порог по IP выше: за одним
  адресом (NAT, терминатор TLS) сидят многие. Снять блокировку раньше:
  `docker compose -f ops/docker-compose.yml exec api python -m api.cli
  unlock-login <логин>` (или `--ip <адрес>`). Команда удаляет из журнала
  неудачные входы этого логина или адреса за последние 15 минут. Одновременно выполняется не больше 8 проверок
  пароля, остальные сразу получают 429 с `Retry-After: 5`. Несуществующий,
  заблокированный и OIDC-логин проверяются против фиктивного хеша, чтобы
  время ответа не выдавало, какие учётки существуют.
- **Проверка Origin** (`backend/api/origin.py`). Запросы POST, PUT, PATCH и
  DELETE под `/api/` (кроме `/api/auth/oidc/`) пропускаются, только если
  `Sec-Fetch-Site` равен `same-origin` или `none`. Если его нет, `Origin`,
  а при его отсутствии `Referer`, должен совпадать с хостом и схемой
  запроса. Иначе ответ 403 «запрос с другого сайта». Запрос без всех трёх
  заголовков (curl, скрипты) пропускается: это защита от чужой страницы
  в браузере, а не от клиента, у которого уже есть cookie. Отказ пишется в
  журнал, только если запрос несёт cookie сессии.
- **Адреса подключений** AD, KSC и VM — только имя хоста или IP, IPv6 без
  зоны `%…` (`backend/api/hosts.py`). При смене адреса или учётной записи сохранённый
  пароль нужно ввести заново.
- `/docs`, `/redoc`, `/openapi.json` выключены по умолчанию
  (`Settings.expose_docs`, `STOOLS_EXPOSE_DOCS=true` — только для отладки).
- Контейнеры API и БД — от непривилегированного пользователя (кроме Caddy:
  обоснование в `frontend/Dockerfile` — порт 80/443 для автоматического
  HTTPS требует root или `CAP_NET_BIND_SERVICE`).
- **Исходящий трафик** — только по действию пользователя или настройке:
  скачивание лент VM (NVD, EPSS, ExploitDB) и бандла ATT&CK по кнопке,
  подключения к AD, KSC, MaxPatrol VM и модели LLM по адресам из настроек,
  провайдер OIDC, ACME при `STOOLS_TLS=auto`; скан описанных сетей и
  DNS-запросы модуля Assets — кнопкой или по расписанию, заданному
  пользователем. Сам по себе стек наружу не ходит.
