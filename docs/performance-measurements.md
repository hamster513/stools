# Замеры производительности и быстрый возврат к спискам

Первый этап оптимизации затрагивает реестр хостов Assets, списки уязвимостей и образов VM и обзоры этих двух модулей. Пагинация API, состав строк и права доступа сохранены.

Списки считаются свежими 120 секунд и остаются в памяти браузера 10 минут после закрытия последнего наблюдателя. Поиск, фильтры, сортировка и вертикальная прокрутка также сохраняются в памяти сессии; явные параметры входящей ссылки имеют приоритет. Загруженные страницы бесконечного списка не обрезаются. Неактуальные запросы отменяются при смене фильтра или уходе. Для нового фильтра до получения его ответа показывается загрузка: строки прежнего отбора не участвуют в массовых действиях.

При выходе, смене пользователя или итоговых прав кэш и состояние экранов очищаются; запоздалые ответы не восстанавливают старые данные. Проверка сессии имеет прежний срок свежести 15 секунд; переход после этого срока сначала проверяет доступ. Изменения через API и завершение заданий продолжают инвалидировать данные. Частота опроса заданий, планировщики и Threat Hunting не меняются. Данные API не записываются в localStorage или IndexedDB.

## Включение измерений API

По умолчанию режим выключен. На время диагностики задайте API переменную `STOOLS_REQUEST_TIMING_ENABLED=true` и пересоздайте только контейнер API с сохранением остальных параметров. После диагностики отключите флаг.

Ответ получает `Server-Timing`: `app` — время до заголовков, `sql` — суммарное время выполнения SQL до заголовков, `sql_count` — число выполнений. `X-Request-ID` генерируется сервером. Журнал `request_timing` дополнительно содержит время передачи всего тела и его размер в байтах до сжатия прокси. SQL включает запросы авторизации; время ожидания соединения, обработка ORM/Python и сериализация входят только в общее время. Для потокового ответа финальные SQL-метрики доступны в журнале. Работа BackgroundTasks после ответа исключена. Необработанный 500 Starlette формирует снаружи пользовательского middleware: у него нет диагностических заголовков, а размер в журнале обозначается `None` (не наблюдался), а не нулём. Время до исключения и выполненный SQL учитываются.

Журнал содержит шаблон маршрута, метод, статус и числа. SQL, параметры, реальные URL объектов, cookie, тела запросов/ответов не записываются. Это дополнительный журнал; настройку обычных access-логов HTTP-сервера он не меняет.

## Read-only benchmark

Используйте отдельный тестовый стенд. Скрипт делает только GET к фиксированным спискам Assets/VM, не сбрасывает кэши PostgreSQL/ОС и не сохраняет ответы. Нагрузку на продовой базе не запускайте.

Сохраните заголовок Cookie тестовой сессии в файл вне репозитория с правами `0600` (например, `stools_session=...`) или передайте через `STOOLS_BENCH_COOKIE`. Не помещайте cookie в команду, историю терминала или отчёт.

```sh
python3 ops/benchmark_lists.py --base-url http://127.0.0.1:18080 \
  --confirm-test-target --cookie-file /private/tmp/stools-bench.cookie \
  --users 1 --samples 10 --output /private/tmp/stools-benchmark-u1.json
```

Повторите с `--users 5` и другим именем отчёта. В JSON/CSV — p50/p95 HTTP, ошибки, размер ответа, время и число SQL. Первый запрос отделён от повторных, фильтр и глубокая страница — отдельные сценарии. Первый запрос не означает холодные кэши ОС/БД. Redirect запрещён, чтобы cookie не ушла на другой адрес. Удалите файл cookie после проверки.

Браузерные замеры дополняют HTTP-отчёт: время до первых строк, число повторных GET при возврате, сохранение фильтра/прокрутки, память после 20 страниц, смена сессии. Одинаковые данные и API обязательны для сравнения интерфейсов. Локальный ARM-профиль не подтверждает производительность продового x86.

## Первый baseline, 18.11.2026

Синтетический профиль S: 10 000 активов, 50 000 наблюдений, 100 000 пар хост–CVE. ARM Mac, Docker: 11 CPU, 7,65 ГиБ RAM; API — один процесс с лимитом 2 ГиБ, PostgreSQL — отдельный контейнер. Рабочая база стенда не участвовала. По 10 повторов каждого HTTP-сценария, без сброса кэшей ОС/БД.

| Сценарий | 1 клиент, p95 | 5 клиентов, p95 |
| --- | ---: | ---: |
| Assets, первая страница | 1 827 мс | 9 413 мс |
| Assets, фильтр | 975 мс | 4 725 мс |
| Assets, offset 3800 | 1 906 мс | 9 114 мс |
| VM, первая страница | 54 мс | 91 мс |
| VM, offset 3800 | 86 мс | 109 мс |

В этих прогонах ошибок HTTP не было. Пик наблюдаемого RSS API: 339 МиБ при одном клиенте и 847 МиБ при пяти; максимальный VmHWM процесса — 941 МиБ. Это лабораторный профиль, не оценка максимальной ёмкости прода. Синхронизации во время базовых замеров не выполнялись; профиль под фоновыми заданиями, 10 клиентов, большой L и нативный x86 остаются отдельными нагрузочными проверками.

Для одного клиента Assets SQL занимает около 51–53 мс при полном HTTP около 1,8–1,9 с. EXPLAIN ANALYZE фактических выборок на синтетической БД: 10 000 активов — 2,3 мс, 50 000 наблюдений — 8,4 мс. Возвращаемая страница при этом содержит 200 строк. Следующий приоритет — сократить загрузку и обработку полного набора объектов в Python/ORM, перенести отбор и пагинацию в SQL и отделить расчёт фасетов. Время SQL в Server-Timing включает ожидание драйвера/передачу результата и планирование потока; это не чистое время выполнения внутри PostgreSQL.

В окончательном образе первый вход в Assets до строк занял 2,5 с. В 20 возвратах из свежего кэша p95 — 19 мс, повторных GET списка — 0. После 16 с выполнена проверка сессии без повторной загрузки списка; поиск и scrollTop 1200 сохранены. Исходный интерфейс также быстро возвращал свежие данные в старом 15-секундном окне, но терял поиск/прокрутку и снова запрашивал список после истечения этого окна. Новая доработка улучшает возврат; первую загрузку ещё предстоит ускорить.

Проверены 20 загруженных страниц каждой таблицы: страницы и глубокая прокрутка восстановлены, повторных GET при возврате нет. JS heap браузера после сборки мусора вырос с 8,2 до 12,4 МиБ для Assets; после добавления 20 страниц VM — с 12,3 до 14,4 МиБ. Истёкшая серверная сессия переводит на вход, прежние строки не показываются.

Целевые проверки: 14 тестов измерений/benchmark и 15 тестов API-клиента/кэша/авторизации. В расширенном наборе границы авторизации остаются три прежних сбоя `test_platform_level_sweep` для deny/read/admin на ручках очереди планировщика; они воспроизведены отдельно на исходном HEAD и не исправлялись этой доработкой.


## Assets: SQL-список и производный индекс (19.11.2026)

Список, обзор и массовый выбор используют один SQL-отбор. Статусы, исполнители и сроки находятся в общих таблицах находок и читаются напрямую. В производном индексе остаются результаты прежнего алгоритма расхождений и поля отбора. Поиск сохраняет буквальный смысл `%`/`_`, Unicode-нормализацию, поиск по пропавшим наблюдениям и AD-cell; ключи находок не меняются.

Ревизия исходных данных меняется транзакционно триггерами PostgreSQL на `asset`, `asset_observation`, `network`, `asset_zone`, `asset_settings`. Один счётчик на транзакцию не замедляет массовые вставки цепочкой обновлений одной строки; перечень изменённых активов отмечает каждую запись. Готовность проверяет ревизию, версию алгоритма, отсутствие необработанных изменений и срок годности. Временные границы неактивности AD и UTC-полночь инвалидируют индекс; свежесть источников для видимых строк считается на момент запроса.

Небольшие ручные изменения (до 200 активов) обновляют затронутые записи до фиксации той же транзакции. После импорта, массового изменения, изменения метаданных или истечения срока общая очередь автоматически перестраивает индекс; проверка необходимости — раз в минуту. Задача `platform/assets_read_refresh/0` видна в общем планировщике, требует администратора платформы для ручного запуска/настройки, объединяет повторы и поддерживает отмену. Threat Hunting не изменён. Пакеты по 500 активов публикуются одним готовым поколением; отмена или конкурентное изменение не публикуют неполный результат.

Для списка, обзора и выгрузки используется единый снимок REPEATABLE READ. Транзакция авторизации предварительно освобождается, второе соединение для экспорта не требуется. CSV читает страницы по 500 активов; при устаревшем/отключённом индексе такой же пакетный расчёт идёт в приватных TEMP-таблицах текущего соединения, без изменения общего индекса. Поэтому роли БД требуется обычное право TEMP на базу. Таблицы удаляются при завершении/отмене транзакции. XLSX сохраняет существующий предел 100000 строк и буфер готового файла; ограничение памяти ORM не означает потоковую передачу готового XLSX.

Откат SQL-списка: `STOOLS_ASSETS_SQL_LIST_ENABLED=false` в окружении API и пересоздание API. Список вернётся к прежнему расчёту, автоматическая перестройка отключится. Добавочные таблицы не удалять и миграцию не откатывать при переключении флага. Ручная задача перестройки остаётся доступна администратору; после обратного включения флага неактуальный индекс корректно заменяется.

Замер S: одна и та же отдельная синтетическая БД (10000 активов/50000 наблюдений), ARM, API 2 ГиБ, PostgreSQL 1 ГиБ, без Redis/браузерного кэша. Десять повторов HTTP на сценарий, кэши ОС/БД не сбрасывались. Это не прогноз для неизвестного x86-прода.

| Сценарий, p95 HTTP | Старый путь, 1 клиент | SQL, 1 клиент | Старый путь, 5 клиентов | SQL, 5 клиентов |
| --- | ---: | ---: | ---: | ---: |
| Первая страница | 1897 мс | 190 мс | 9335 мс | 200 мс |
| Новый фильтр | 1123 мс | 152 мс | 4690 мс | 256 мс |
| Страница с offset 3800 | 1906 мс | 81 мс | 8911 мс | 310 мс |

Итоговый набор Assets и очереди: 610 passed, 2 skipped, три существующих падения тестов DNS/RackTables расписаний. Те же три падения воспроизведены на чистом HEAD 5c61c10. Новые проверки отдельно покрывают совпадение выдачи/фасетов/массовых ключей, решения и конкурентные изменения, атомарность/отмену, временные границы, экспорт нескольких страниц и пул из одного соединения. Нагрузки на продовой базе и реальные замеры x86 не проводились.

Дополнительный профиль **Assets-L**: 100000 активов и 500000 наблюдений; VM остался на S, это не полный L из общего плана. P95 первой страницы — 503 мс (один клиент) / 668 мс (пять), фильтра — 240 / 421 мс, страницы с offset 98000 — 535 / 649 мс. По 10 повторов, ошибок нет. Пик RSS API по VmHWM — 216,4 МиБ. Полный L с 2 млн пар VM и реальный продовый x86 не измерены. Первый прогон Assets-L с параллельным обновлением Graphify сохранён отдельно и не использован в этой таблице.

EXPLAIN ANALYZE на Assets-L: фасеты ~459 мс, выбор 200 ID с offset 98000 ~34 мс. Основной остаточный расход — агрегирование фасетов (временные данные около 74 МиБ на запрос), а не сортировка страницы; дополнительные индексы на бизнес-таблицы не добавлялись. Используются первичные индексы производных таблиц и существующий индекс связи наблюдения с активом. Следующий этап плана — кэш/дальнейшая оптимизация агрегатов, с сохранением актуальности.
