# Harbor и образы контейнеров в VM

Модуль VM читает из Harbor образы контейнеров и отчёты встроенного сканера Trivy
и показывает их на странице «Образы контейнеров». Сканирует Harbor, STools
ничего не запускает: он только забирает готовые отчёты и считает риск находок по
формуле VM. Маршруты — `docs/vm/api.md`, раздел «Harbor»; дизайн —
`docs/superpowers/specs/2026-10-28-harbor-images-design.md`.

Проверено на Harbor 2.15.4 (28.10.2026). Другие версии 2.x должны работать, если
отдают отчёт Trivy в формате `application/vnd.security.vulnerability.report;
version=1.1` (с Harbor 2.2); если такого ключа нет, берётся `version=1.0`.
Если у образа в обзоре скана нет ни того, ни другого ключа, STools считает его не
сканированным (`none`), и он учитывается в `skipped_unscanned`. Если же обзор
скана есть, а в самом отчёте образа нет ни одного из этих ключей, образ остаётся
со статусом Harbor, в его пометку об ошибке (`sync_error`) записывается
`BAD_FORMAT`, прежние находки образа не меняются.

## Установка Harbor (тестовый экземпляр)

У заказчика Harbor обычно уже есть: тогда этот раздел не нужен, переходите к
разделу про проекты и робота. Для проверки STools Harbor поднимается рядом со
стендом.

1. Скачайте онлайн-установщик `harbor-online-installer-v2.15.4.tgz` со страницы
   релизов goharbor/harbor и распакуйте его в каталог вне репозитория, например
   `~/harbor`. Нужен Docker с Compose v2.
2. Скопируйте `harbor.yml.tmpl` в `harbor.yml`. Образец с нужными ключами —
   `ops/harbor/harbor.yml.example`; это не самостоятельный файл, а набор ключей,
   которые нужно привести к этим значениям в `harbor.yml` из установщика. Что
   менять:

   | Ключ | Значение |
   |---|---|
   | `hostname` | `localhost` для проверки на своём компьютере, на сервере — имя из DNS |
   | `http.port` | свободный порт, например `8082` (порт 80 может быть занят) |
   | `https` | для HTTP-only теста раздел закомментирован целиком |
   | `harbor_admin_password` | случайный пароль вместо `CHANGE_ME` |
   | `database.password` | другой случайный пароль |
   | `data_volume` | каталог данных, например `/data/harbor`; на Docker Desktop он должен быть разрешён в Settings → Resources → File sharing |
   | `trivy.ignore_unfixed` | `false` — в отчёте и уязвимости без исправления |
   | `trivy.skip_update` | `false` — база Trivy скачивается при первом скане, нужен интернет |
   | `trivy.offline_scan` | `false`; `true` — только если базу загрузили заранее |
   | `log.local.location` | каталог логов, по умолчанию `/var/log/harbor` |

   Права на готовый `harbor.yml` — 600: в нём пароли.
3. Запустите `./install.sh --with-trivy` (пользователь должен иметь доступ к
   Docker). Установщик скачивает образы и создаёт `docker-compose.yml`. Дальше Harbor управляется командами `docker compose` из
   каталога установки; интерфейс — `http://localhost:8082`, логин `admin`.

### Apple Silicon

Официальные образы Harbor собраны только под amd64; нативные arm64 появятся
в версии 2.16 (сейчас предрелиз). На Apple Silicon Docker Desktop запускает
Harbor под эмуляцией: он медленнее, но работает. Девять контейнеров Harbor
занимают около 1,5–2 ГБ памяти — учитывайте это в лимитах Docker Desktop.

### Docker Desktop: ошибка с `root.crt`

Docker Desktop (файловая система virtiofs) не принимает вложенный файловый
bind-mount, который создаёт установщик: `data/secret/registry/root.crt` →
`/etc/registry/root.crt` внутри каталога `/etc/registry/`. Контейнер registry не
стартует с ошибкой «mountpoint … is outside of rootfs». Обход:

1. Скопируйте `root.crt` из `<data_volume>/secret/registry/` в
   `common/config/registry/` каталога установки (рядом с конфигом registry — этот
   каталог монтируется целиком).
2. Удалите из сгенерированного `docker-compose.yml`, в сервисе `registry`,
   строку монтирования файла `…/root.crt:/etc/registry/root.crt`.
3. Выполните `docker compose up -d`.

Повторять нужно после каждого `./prepare` или повторного `install.sh`, потому что
`docker-compose.yml` пересоздаётся. На Linux-сервере правка не нужна.

## Проекты и автоскан

Образ попадает в STools, только если Harbor его просканировал. Чтобы сканирование
шло само, в проекте включают «автоскан при push» (`auto_scan = true` в метаданных
проекта). Через интерфейс: проект → Configuration → «Automatically scan images on
push». Через API:

```bash
curl -sS -u "admin:$HARBOR_ADMIN_PASSWORD" -X PUT \
  -H 'Content-Type: application/json' \
  -d '{"metadata": {"auto_scan": "true"}}' \
  http://localhost:8082/api/v2.0/projects/library
```

Проект `library` есть по умолчанию; свои создаются в интерфейсе или
`POST /api/v2.0/projects`. Образы, отправленные до включения автоскана, нужно
просканировать вручную (Scan в интерфейсе): STools сам сканирование не запускает.

### Мультиархитектурные образы

Обычный `docker push` образа, скачанного с `docker pull`, отправляет образ одной
архитектуры. Мультиархитектурный образ отправляется индексом манифестов:

```bash
docker login localhost:8082
docker buildx imagetools create -t localhost:8082/library/alpine:3.18 alpine:3.18
```

Harbor сканирует индекс целиком: отчёт и обзор скана лежат на индексе, у
дочерних манифестов их нет. Поэтому STools хранит один образ на индекс, а в поле
«платформа» пишет платформы детей через «, » (`linux/amd64, linux/arm64`; записи
с `os = unknown` — аттестации — пропускаются). У обычного образа платформа не
указана. `localhost` Docker по умолчанию считает небезопасным реестром, поэтому
для HTTP-экземпляра на этом же компьютере настраивать `insecure-registries` не
нужно; для другого адреса — нужно.

## Робот

STools входит в Harbor под учётной записью-роботом системного уровня с правами
только на чтение. Создайте его в Harbor: Administration → Robot Accounts → New,
уровень System, срок — по политике, «Never expire» допустим для стенда. Права:

| Вид (kind) | Область | Ресурс и действие |
|---|---|---|
| `system` | — | `project`: `list` |
| `project` | `*` — все проекты | `project`: `read` |
| | | `repository`: `list`, `read`, `pull` |
| | | `artifact`: `list`, `read` |
| | | `artifact-addition`: `read` |
| | | `scan`: `read` |
| | | `tag`: `list` |

То же через API (секрет приходит в ответе один раз — сохраните его сразу и
никому не пересылайте; в этом документе его нет):

```bash
curl -sS -u "admin:$HARBOR_ADMIN_PASSWORD" -X POST \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "stools-reader", "level": "system", "duration": -1,
    "description": "STools: чтение образов и отчётов Trivy",
    "permissions": [
      {"kind": "system", "namespace": "/",
       "access": [{"resource": "project", "action": "list"}]},
      {"kind": "project", "namespace": "*", "access": [
        {"resource": "project", "action": "read"},
        {"resource": "repository", "action": "list"},
        {"resource": "repository", "action": "read"},
        {"resource": "repository", "action": "pull"},
        {"resource": "artifact", "action": "list"},
        {"resource": "artifact", "action": "read"},
        {"resource": "artifact-addition", "action": "read"},
        {"resource": "scan", "action": "read"},
        {"resource": "tag", "action": "list"}]}]}' \
  http://localhost:8082/api/v2.0/robots
```

Полное имя робота — `robot$stools-reader` (Harbor добавляет префикс
`robot$`); его и вводят в STools в поле «Имя робота».

- **`artifact-addition: read` обязателен.** Без него отчёт об уязвимостях
  закрытого (private) проекта отвечает 403 FORBIDDEN: отчёт образа не
  прочитается, образ получит пометку об ошибке, а его репозиторий попадёт в
  список ошибок синхронизации. Публичный проект работает и без этого права,
  поэтому ошибка легко остаётся незамеченной — проверяйте на закрытом проекте.
- **Уровень и имя робота правкой не меняются.** `PUT /api/v2.0/robots/{id}` их
  не принимает (права в пределах того же уровня править можно). Нужен другой
  уровень или имя — создайте нового робота (старый удалите) и введите в STools
  его имя и секрет.

## Подключение в STools

«Настройки → VM → Harbor» (admin): адрес (`http://` или `https://`, без
завершающего «/», имени и пароля, `?…` и `#…`: учётные данные в адресе попали бы
в журнал и сообщения задач, робот задаётся отдельными полями), имя робота, секрет, «проверять TLS»,
проекты (пусто — все, доступные роботу) и число последних тегов на репозиторий
(по умолчанию 10, от 1 до 100). «Проверить подключение» читает версию Harbor и
список проектов под роботом; в ответе только класс причины отказа (`NO_LINK`,
`TLS_FAILED`, `LOGIN_REJECTED`, `NO_RIGHTS`, `server_error(код)`, `BAD_FORMAT`,
`HTTP <код>`; если сохранённый секрет не удалось расшифровать — его текст).
Если у пользователя уже идут две проверки, третья отвечает 429. При смене
адреса, имени робота или флага TLS секрет вводится заново. «Синхронизировать
сейчас» (write) запускает задачу; расписание задаётся там же.

### Адрес Harbor из контейнера API

Адрес, который вы вводите, должен быть виден из контейнера `api`, а не из
браузера.

- **Docker Desktop (Mac, Windows).** Harbor на том же компьютере доступен как
  `http://host.docker.internal:8082`. `localhost` из контейнера — это сам
  контейнер.
- **Linux-сервер.** Имя `host.docker.internal` в контейнере по умолчанию нет.
  Либо укажите обычный адрес Harbor (имя из DNS или IP сервера), либо добавьте в
  сервис `api` в compose:

  ```yaml
  extra_hosts:
    - "host.docker.internal:host-gateway"
  ```

### HTTPS и корпоративный центр сертификации

Для HTTPS-адреса оставьте «проверять TLS» включённым. Если сертификат Harbor
выпущен корпоративным УЦ, ему должен доверять контейнер API: он использует общий
файл сертификатов сервера (`SSL_CERT_FILE`), который прод-compose монтирует из
`${STOOLS_CA_BUNDLE}`. Как проверить и добавить корневой сертификат —
`docs/install.md`, раздел «Корпоративный УЦ». Отключать проверку TLS ради
самоподписанного сертификата не стоит: секрет робота уйдёт на непроверенный
адрес.

## Что синхронизируется

Синхронизация обходит проекты (из настроек или все доступные роботу), их
репозитории и артефакты.

- **Только тегированные артефакты.** Слои, подписи, SBOM и аттестации без тегов
  пропускаются.
- **`tags_per_repo` самых свежих** по времени отправки в каждом репозитории.
  Harbor отдаёт тегированные артефакты свежими первыми (`sort=-push_time`,
  `q=tags=*`), STools листает список, пока не наберёт `tags_per_repo` разных
  digest, и остальную историю репозитория не читает. Образ, вытесненный лимитом,
  из STools удаляется.
- **Статусы скана** образа: `success`, `pending`, `running`, `error`, `none`
  (не сканировался). Отчёт читается только у `success`. Новый образ с другим
  статусом хранится без находок; образ, у которого находки уже были, при
  повторном скане в другом статусе сохраняет прежние находки и время скана.
  Число таких образов — `skipped_unscanned` в итоге синхронизации.
- **Отчёт читается заново только при новом скане** (изменилось время скана
  образа) или если у образа ещё нет находок. Находки одного образа с одним
  ключом (идентификатор, пакет, установленная версия) схлопываются: остаётся
  самая серьёзная.
- **Исчезнувшее удаляется** — образы, которых больше нет в успешно прочитанном
  репозитории или проекте. Образы проекта, убранного из списка «проекты» в
  настройках, тоже удаляются: сужение списка очищает данные по остальным
  проектам. Если проект или репозиторий прочитать не удалось,
  его образы остаются как были с пометкой причины, а в итоге синхронизации
  сохраняются имя объекта, этап, безопасная причина и HTTP-код. В настройках
  свёрнутый блок «Подробности ошибок (N)» раскрывает причину, действие для проверки
  и список объектов; одинаковые ошибки
  сгруппированы. Старые записи без причины отмечены явно: подробности появятся
  после повторной синхронизации. `last_sync.errors` остаётся списком имён,
  `last_sync.error_details` содержит подробности. Детали хранятся в существующем
  поле журнала, миграция БД не требуется. Не прочитался вход или список проектов — задача
  завершается ошибкой, данные не меняются.
- **Защита от пустого списка проектов.** Если проекты не заданы в настройках, а
  Harbor не вернул ни одного (чаще всего у робота нет прав), а образы в STools
  уже есть, задача падает с сообщением «Harbor не вернул ни одного проекта:
  проверьте права робота», и ничего не удаляется. Первая синхронизация в пустую
  базу с пустым реестром проходит без ошибки.
- **Пока идёт повторный скан или он упал**, образ сохраняет прежние находки,
  время скана, сканер и счётчики Trivy: обзор Harbor в это время без сводки, и
  счётчики не обнуляются.
- **Истории нет**: хранится последнее состояние, как и у хостов VM.

Синхронизация не идёт одновременно с импортом VM, пересчётом и загрузкой архива
справочников: все они пересобирают витрину CVE и риск (409 при попытке запуска;
расписание в этом случае пропускает запуск). Свежесть показывает строка «Образы
контейнеров (Harbor)» в сводке «Данные»: устаревает через 7 дней.

## Риск находок образов

Риск считается по аддитивной скоринговой модели VM с теми же справочниками
(EPSS, KEV, NVD, ExploitDB, Metasploit, GHSA), что и для хостов. Порог High — 80,
правила повышения срочности KEV общие. Сеть, критичность и конфиденциальность
для образа считаются неизвестными: свойства хостов в его оценку не входят.

Находки CVE и GHSA получают оценку при наличии данных в витрине `vm_cve`.
Идентификаторы без записи в витрине сохраняются без риска; для них доступна
оценка Trivy. Образ без оценённых находок показывает «—». Сводка содержит
наибольший риск и число находок после объединения эквивалентных CVE/GHSA для
одного пакета и установленной версии.

Полный пересчёт и обновление справочников проверяют все находки, но записывают
только изменившиеся оценки и сводки. При импорте хостов MaxPatrol обрабатываются
только находки Harbor без оценки, для которых доступна запись в витрине CVE,
и сводки затронутых образов. Повторный импорт хостов не переписывает весь Harbor.

## Ограничения первой версии

- Проверено только на Harbor 2.15.4; отчёт Trivy — MIME `version=1.1`, запасной
  вариант `1.0`.
- Только просмотр: статусов находок и принятия риска для пар «образ × CVE» нет.
- Сканирование из STools не запускается; проекты Harbor из STools не
  настраиваются.
- Нет привязки образа к активам Assets и к хостам, где он запущен; образы не
  входят в общий список «Уязвимости» и в плитки обзора VM.
- Только Harbor и Trivy: другие реестры и сканеры не поддерживаются.
- Хранятся не больше `tags_per_repo` свежих тегов на репозиторий.


## Тип артефакта и политика скачивания

На странице «Образы контейнеров» отдельная колонка «Тип» различает контейнерные
образы, Helm-чарты, другие артефакты и пока не определённый тип. Тип берётся из
`type`, `media_type`, `artifact_type` Harbor; общий OCI manifest сам по себе не
доказывает, что это образ контейнера. Старые записи уточняются следующей
синхронизацией. Фильтр «Тип артефакта» действует на список, счётчики и CSV/XLSX;
в API — повторяемый `artifact_kind=image|helm|other|unknown`.
Helm-чарты не сопоставляются с запущенными контейнерами.

«Скачивание · уязвимости» — оценка блокировки по уязвимостям по последней
синхронизации. В карточке под стрелкой доступны причина, время получения
настроек, порог, источник исключений и до 20 идентификаторов каждого списка.

- `prevent_vul=false`: блокировка по уязвимостям отключена.
- При включённой блокировке CVE с критичностью **на уровне порога или выше**
  блокирует скачивание, если не входит в действующий список исключений.
- `reuse_sys_cve_allowlist=true` применяет общий список `/system/CVEAllowlist`;
  иначе применяется **только проектный** `cve_allowlist`. Списки не складываются.
- Срок действия списка проверяется при открытии страницы. После истечения
  исключения не применяются, даже если новая синхронизация ещё не запускалась.
- Неуспешный или незавершённый скан блокирует образ при включённой политике.
  Без отчёта или доступных настроек показывается «Недостаточно данных».
  Полнота загруженного отчёта проверяется по числу находок из обзора скана.
- Для мультиархитектурного индекса решение зависит от дочернего манифеста
  выбранной платформы; общий отчёт не даёт разрешения для всех платформ.
- Для Helm и других артефактов оценка по отчёту контейнерного образа не применяется.

Исключения не удаляют находки и не понижают их риск в STools. Настройки проектов
читаются при каждой синхронизации, даже без нового скана. Ошибка чтения не
позволяет сохранить прежний зелёный статус. Учётной записи STools нужен доступ
к чтению проекта и выбранного списка исключений. Числовое имя проекта передаётся
с `X-Is-Resource-Name: true`.

Это **не проверка прав пользователя на pull или наличия подписи**. В проекте с
обязательной подписью карточка напоминает об этом отдельном условии. Изменения
