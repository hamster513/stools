# Роли, группы и уровни доступа

Права в STools — уровни по областям. **Роль** — набор уровней (по одному на
каждый модуль и на платформу), **группа** получает роль, **пользователь**
получает права через свои группы. Группа бывает локальной (членов назначает
администратор) или из OIDC (членство приходит из claim провайдера при входе).
Можно дать человеку запись в SIEM и только чтение в VM, закрыть модуль целиком
или разрешить аналитику настраивать подключения своего модуля, не делая его
администратором платформы.

Механизм — `backend/api/rbac.py` (что нужно запросу) и
`backend/api/platform/services/access.py` (роли, группы, членство, самоблокировка).
Интерфейс — `/settings/roles`, `/settings/groups`, `/settings/users`.
Контракт ручек — `docs/api-contract.md`: «Общие правила» (правило и текст отказа),
«Аутентификация» (пересчёт членства при входе по OIDC), «Общие настройки»
(пользователи, роли, группы, членство).

## Области и уровни

Области: модули `attack`, `siem`, `vm`, `ad`, `ksc`, `assets`, `toolbox` и
`platform`. Уровни по возрастанию, каждый включает предыдущие:
`deny` < `read` < `write` < `admin`.

### Модуль

| Уровень | Название в интерфейсе | Что разрешено |
|---|---|---|
| `deny` | Запрет | ничего под `/api/<модуль>/`, включая чтение; модуля нет в рейке |
| `read` | Аудитор | все чтения и выгрузки |
| `write` | Аналитик | + работа с данными: статусы, исполнители и комментарии находок, загрузка выгрузок и импорт, запуск и отмена заданий и сбора, пересчёт и переразбор, синхронизация, задания ToolBox, правки активов |
| `admin` | Администратор | + настройка модуля: подключения и источники, их проверка и расписания, формы настроек модуля, справочники, профили, зоны, база ATT&CK |

### Платформа

Платформа — пользователи, группы, роли, правила сессий, OIDC, журнал действий,
модель LLM и настройки статусов находок. Уровня `write` у платформы нет:
сервер отвергает его при сохранении роли (`422`), в интерфейсе три переключателя.

| Уровень | Название в интерфейсе | Что разрешено |
|---|---|---|
| `deny` | Запрет | только свой профиль и сессия (`/api/auth/*`) и то, что открыто всем (ниже) |
| `read` | Чтение | чтение пользователей, групп, ролей, журнала действий, правил сессий, настроек OIDC (секрет клиента не отдаётся) |
| `admin` | Администратор | + любая запись под `/api/settings/` (кроме матрицы ATT&CK, см. ниже) |

## Правило проверки

Одно правило на всё приложение: зависимость `require_access` стоит на каждом
роутере, поэтому новая ручка защищена по умолчанию. Тест
`backend/tests/api/test_auth_boundary.py` перебирает все ручки и падает на
пишущей ручке, которую не учли в таблицах ниже.

Какая область и какой уровень нужны запросу (`needed(method, path)` в `rbac.py`):

| Запрос | Нужно |
|---|---|
| `/api/auth/*` (профиль, пароль, тема, выход, вход по OIDC) | любой вошедший |
| `/api/<модуль>/…`, чтение (GET, HEAD, OPTIONS) | `read` в модуле |
| `/api/<модуль>/…`, запись | `write` в модуле; для ручек из списка ниже — `admin` |
| `/api/settings/…`, чтение | `platform` не ниже `read` |
| `/api/settings/…`, запись | `platform = admin` |
| `GET /api/settings/llm`, `/findings`, `/data-status`, `/attack…` | любой вошедший: их показывают страницы модулей |
| `/api/settings/attack…`, запись | `admin` в `attack` |
| `/api/findings/*`, `/api/users/directory` | вход любой; уровень в модуле находки проверяет сама ручка (ниже) |
| прочее, чего нет в таблице | `platform = admin` |

Отказ — `403 {"detail": "нет доступа: <область>, нужен уровень <название>"}`;
названия: «запрет», «аудитор», «аналитик», «администратор» (для платформы
чтение тоже подписано «аудитор»).

Исключения из таблицы:

- **Сводка «Данные»** (`/api/settings/data-status`) открыта всем, но в ответе
  остаются только модули, открытые вызывающему на чтение.
- **Находки.** «Мои находки» (`mine`, `mine/count`, `mine/export`) — любой
  вошедший, строки отбираются по модулям с уровнем `read` и выше. Состояние
  находки (`GET /api/findings/state`) и сводка (`/summary`) требуют `read` в
  запрошенном модуле, иначе `403`. Смена статуса, исполнителя,
  срока, комментарий и массовые правки требуют `write` в модуле находки;
  находки Threat Hunting (модуль `siem_th`) относятся к области `siem`.
  Принять риск вправе тот, чей уровень в модуле находки не ниже заданного
  настройкой «кто может принимать риск» (`risk_accept_role`: `write` — «аналитик
  модуля», `admin` — «администратор модуля»).
- **Справочник исполнителей** `GET /api/users/directory?module=<модуль>`
  (параметр обязателен) отдаёт активных пользователей с уровнем `write` и выше
  в этом модуле; назначить находку можно только им. Спросить список может
  только тот, у кого самого `write` в этом модуле, иначе `403`.
- **ToolBox.** Полные значения в скраббере видит `toolbox ≥ write`, остальные —
  скрытые.

### Что требует `admin` в модуле

Всё прочее, что пишет под `/api/<модуль>/`, — `write`. Уровень `admin`
нужен только записи из списка `MODULE_ADMIN_WRITES` в `rbac.py`:

| Модуль | Запись уровня «Администратор» |
|---|---|
| AD, Антивирус (`ad`, `ksc`) | подключения: создание, правка, удаление, проверка, расписание |
| AD, Антивирус, VM, SIEM, Assets, ToolBox | `PUT /api/<модуль>/settings`; у VM ещё проверка подключения (`settings/test-vm`) |
| SIEM | подключение к базе знаний (`mp`) и его проверка; профиль и его предпросмотр; справочник ATT&CK для SIEM (загрузка, удаление, применение); настройки и планировщик Threat Hunting |
| VM | зоны; загрузка и скачивание справочников (`refs`) |
| ToolBox | удаление псевдонима (необратимо: забытый псевдоним может достаться другому значению) |
| Assets | источники DNS, сети и RackTables: создание, правка, удаление, проверка, расписание; правила зон; зоны; расписание синхронизации |
| ATT&CK | обновление матрицы и её задания (`/api/settings/attack…`); загрузка применяемости техник в России (`/api/attack/ru-ttp`) — `write` |

Запуск уже настроенного: «Собрать сейчас», запуск скана сети, DNS и
RackTables, синхронизация, импорт, пересчёт — это `write`.

## Роли

Роль — имя, описание и матрица: уровень на каждый модуль и на платформу.
Отсутствующая область — `deny`. Три роли встроенные:

| Роль | Модули | Платформа |
|---|---|---|
| Администратор | `admin` везде | `admin` |
| Аналитик | `write` везде | `deny` |
| Аудитор | `read` везде | `deny` |

- «Администратор» не редактируется (`409`); при каждом старте API ему
  возвращается полная матрица, в том числе по модулям, добавленным позже.
- «Аналитик» и «Аудитор» редактируются, но не переименовываются.
- Встроенные роли не удаляются. Роль, назначенную группе, удалить нельзя
  (`409`), пока группе не назначена другая.
- Имя роли уникально.

## Группы и членство

Группа — имя, роль и источник:

- **Локальная** (`local`). Членов назначает администратор: в карточке группы
  или в карточке пользователя (полная замена списка).
- **Из OIDC** (`oidc`). У группы есть «имя в OIDC» — значение из claim
  провайдера (имя или идентификатор группы, уникально). Членов задать вручную
  нельзя (`409`), список в карточке только для чтения. Источник после
  создания не меняется.

Встроенные группы «Администраторы», «Аналитики», «Аудиторы» заводятся с
ролями-тёзками при первом старте вместе с ролью и больше не возвращаются:
удалённую локальную группу восстановить нельзя, создайте новую (исключение —
`create-user --group` на сервере, см. ниже). Остальные группы создаёт
администратор платформы.

**Итоговые права пользователя** — максимум по его группам на каждой области.
Нет групп — везде `deny`: вход разрешён, рейка не показывает ни одного доступного модуля (заглушки «в
разработке» могут остаться), открывается профиль.
Кэша между запросами нет: смена роли, группы или членства действует со
следующего запроса, сессии не сбрасываются.

**Членство по OIDC** пересчитывается при каждом входе: значения claim точно
сравниваются с «именем в OIDC» групп, совпавшие группы выдаются, прочие
OIDC-группы человека пропадают. Локальные группы, назначенные такой учётке,
вход не трогает. Если после пересчёта ни одной группы (ни OIDC, ни
локальной) — вход отклонён (`oidc_no_role`), а новая учётка не заводится.

## Что показывает интерфейс

| Элемент | Условие |
|---|---|
| Модуль в рейке | `read` и выше; заглушки «в разработке» видны всем |
| Прямая ссылка на закрытый модуль | экран «Модуль недоступен вашим группам» |
| «Мои находки» в рейке | `write` хотя бы в одном модуле; без него в рейке подпись «только чтение» |
| Кнопки данных (загрузка, импорт, запуск сбора, смена статуса) | `write` в модуле |
| Кнопки настройки модуля (подключения, расписания, справочники, зоны) | `admin` в модуле |
| Настройки → «Данные» (сводка) и «Мой профиль», «Статусы находок» | всем (менять статусы находок — `platform = admin`) |
| Настройки → Платформа: «Пользователи», «Группы», «Роли», «Безопасность», «Вход по OIDC», «Журнал действий» | `platform` не ниже `read`; изменять — `admin` |
| Настройки → «Модель LLM» | `platform = admin` |
| Настройки → Модули → страница модуля `/settings/<модуль>` | `write` в модуле |
| Настройки → «База ATT&CK» (`/settings/attack`) | страница — `write` в `attack`; обновление матрицы — `admin`, загрузка применяемости техник в России — `write` |

Страница настроек модуля делится по уровням. Аналитику (`write`) доступны
загрузки: выгрузки, импорт, сбор, синхронизация. Разделы настройки —
подключения, расписания, формы настроек, справочники, зоны, профили — видны
только администратору модуля (`admin`). Переход по адресу раздела настроек без нужного уровня
показывает экран «Раздел настроек недоступен», а не `403`.

Интерфейс решает только, показывать ли элемент; доступ всегда проверяет
сервер.

## Самоблокировка

Перед фиксацией любой из операций проверяется (`guard_last_admin`):

- правка и удаление роли;
- смена роли, имени и «имени в OIDC» группы, удаление группы;
- изменение членов группы и групп пользователя;
- блокировка и удаление пользователя.

Если после операции нет ни одного активного пользователя с
`platform = admin`, ответ `409` «нельзя оставить систему без администратора».
Если актор опустил собственный `platform` ниже `admin` (операцией над собой,
своей группой или ролью), ответ `409` «нельзя снять права с себя» — даже
когда другие администраторы есть. Транзакция откатывается целиком. Блокировать
и удалять самого себя тоже нельзя (`409`).

**Исключение — вход по OIDC.** Пересчёт членства при входе этой защиты не
проходит: если администратору убрали группу в каталоге, он при следующем входе
больше не администратор, даже если был последним. Система может остаться без
администратора.

Выход: на сервере создать нового локального администратора командой

```bash
docker compose -f ops/docker-compose.yml exec api python -m api.cli create-user <логин> --group Администраторы
```

Это заведёт **новую** локальную учётку с паролем; вернуть права уже
существующему логину команда не может (`пользователь уже существует`).
Зайдя под ней, назначьте нужным людям группу «Администраторы» (или другую с
`platform = admin`) или поправьте группу в OIDC.

Если встроенной группы, названной в `--group`, нет (её удалили или
переименовали), команда заводит её заново со встроенной ролью-тёзкой. Если в
системе нет активного администратора платформы, а названные группы не дают
`platform = admin` (например, «Администраторам» назначили «Аудитора»),
команда завершается с ошибкой, называя группы и их роли, и ничего не создаёт.

## CLI

`python -m api.cli create-user <логин> [--group <имя>]…` — пароль спрашивается
дважды и никуда не пишется. `--group` принимает имя **локальной** группы и
повторяется; без него первый пользователь попадает в «Администраторы», каждый
следующий — в «Аналитики». Неизвестная или OIDC-группа — ошибка, учётка не
создаётся; недостающая встроенная группа заводится заново, а учётку без
`platform = admin` в системе без администратора команда не создаёт (см. выше). CLI сам заводит встроенные роли и группы, если API ещё не
стартовал.

## Журнал действий

В журнале и его CSV колонка `role` («роль») оставлена ради внешних скриптов,
но теперь хранит имена групп актора через запятую (на момент действия).
Правки ролей, групп и членства пишутся как все записи под `/api/settings/`.

## Миграция с прежних ролей

Прежняя схема — одна роль на учётку (`admin`, `analyst`, `auditor`).
Три миграции цепочки: `e5a1c7b3d902` (таблицы, встроенные роли и группы,
членство, OIDC-группы), `a7c3e9f1b204` (колонка `audit_event.role` становится
Text, чтобы вместить имена групп актора) и `7e31b0364015` (удаление
`app_user.role`). В итоге:

- создают встроенные роли и группы; учётки раскладываются по группам по
  прежней роли (`admin` → «Администраторы», `analyst` → «Аналитики»,
  `auditor` → «Аудиторы»), колонка `app_user.role` удаляется; учётки OIDC
  членство получают при следующем входе (из claim), до него прав у них нет;
- пары «группа OIDC → роль» из настроек входа становятся группами с
  источником OIDC (имя и «имя в OIDC» — прежнее значение; если имя совпало с
  локальной группой — `<имя> (OIDC)`; при повторе одной группы берётся
  широчайшая роль); поле `group_roles` из настроек исчезает.

Настройка «кто может принимать риск» миграциями не переписывается: старые
значения `analyst` → `write` («аналитик модуля») и `admin` → `admin`
(«администратор модуля») переводятся при чтении настройки
(`FindingSettings`, `backend/api/platform/findings/core.py`), а в базе значение
меняется при следующем сохранении настройки.

Прежние аналитики настраивали подключения модулей; после миграции встроенный
«Аналитик» — `write`, и настройка модулей осталась у администратора (решение
владельца). Вернуть её отдельным людям — отдельной ролью с `admin` в нужном
модуле и группой для неё.

Откат (`alembic downgrade`) восстанавливает колонку по максимуму из групп:
`platform = admin` — admin, иначе `write` и выше где-либо — analyst, иначе
auditor; OIDC-группы собираются обратно в пары. Пользовательские роли и
группы пропадают вместе с таблицами.
