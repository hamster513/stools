# Статусы находок

Один жизненный цикл находки во всех модулях: AD, Антивирус, SIEM, VM, Assets.
Механизм — платформа (`backend/api/platform/findings/`), модули подключаются
адаптером. Интерфейс — общие компоненты `frontend/src/platform/findings/`.

## Статусы

| Код | Название | Кто ставит | Открытая |
|---|---|---|---|
| `new` | Новая | система (нет строки состояния) | да |
| `in_work` | В работе | человек | да |
| `risk_accepted` | Принят риск | человек, обоснование обязательно | нет |
| `false_positive` | Ложное срабатывание | человек, обоснование обязательно | нет |
| `fixed` | Исправлено | человек (ждёт подтверждения данными) | да |
| `resolved` | Устранена | система | нет |
| `reopened` | Переоткрыта | система | да |

Человек ставит `new`, `in_work`, `risk_accepted`, `false_positive`, `fixed`;
`resolved` и `reopened` ставит только система.

## Переходы

| Событие | Что происходит |
|---|---|
| ключ есть в данных, строки состояния нет | статус `new`, строка не заводится |
| ручная смена | запись состояния и событие истории; `risk_accepted` и `false_positive` без обоснования — отказ |
| ключа нет в свежих данных, статус `new`, `in_work`, `fixed`, `reopened` | → `resolved`, событие системы со ссылкой на снапшот или импорт |
| ключ снова в данных, статус `resolved` (или `fixed`, пока находки не было) | → `reopened`; исполнитель и срок сохраняются |
| ключа нет в данных, статус `risk_accepted`, `false_positive` | статус не меняется, `present = false` |
| `risk_until` раньше сегодняшнего дня, статус `risk_accepted` | → `new`, событие `risk_expired` (ежесуточно, см. ниже) |
| `due_date` раньше сегодняшнего дня, статус открытый | статус не меняется, признак `overdue` |

`fixed` при находке, которая осталась в данных, остаётся `fixed` до её
исчезновения (→ `resolved`). «Сегодня» — дата в поясе `STOOLS_TZ`.

Сверка и ручная смена одной области идут по очереди (блокировка области в
Postgres): сверка не перетирает смену, сделанную, пока она шла.

### Истечение принятого риска

Расписание платформы `platform/risk_expiry` (таблица `platform_schedule`)
заводится при старте API, если его нет, и срабатывает раз в сутки; первый
запуск — на ближайшем тике планировщика после первого старта. Перезапуск API
срок запуска не сдвигает. Риск со сроком «сегодня» истекает на следующий день.

## Автоматика по модулям

| Модуль | Область (`scope_id`) | Ключ | Когда сверяется | Условие автоматики |
|---|---|---|---|---|
| AD | id домена | `finding.key` | конец импорта, пересчёта, удаления снапшота | только последний снапшот домена и только если он и предыдущий посчитаны одной версией анализатора (`analyzer_version`) |
| Антивирус | id сервера KSC | `finding.key` | то же | то же |
| SIEM | 0 | `object_uuid\|kind\|<подпись>` | конец загрузки, переразбора, сохранения профиля | активный снапшот (последний разобранный) посчитан той же версией разбора (`parser_version`) и с тем же отпечатком профиля (`profile_hash`), что предыдущий разобранный, — чем бы он ни был пересчитан; у первого снапшота сравнивать не с чем |
| VM | 0 | `hostname\|ip\|cve` | конец импорта | каждый импорт |
| Assets | 0 | `asset_id\|code`; у `stale`/`conflict` — `asset_id\|code\|source\|field` | конец синхронизации, скана, обновления DNS; после объединения, отвязки, закрепления поля, смены сети актива | каждый раз |

Если условие не выполнено, статусы и история не меняются: у строк
обновляются только наличие (`present`), подпись и тяжесть, в журнал API —
предупреждение. Автоматика вернётся со следующими данными, посчитанными так
же, как предыдущие.

AD, Антивирус, SIEM: находке, пропавшей с прошлых данных без решения людей,
заводится строка — исчезновение закрывает её системой (`resolved`) с
событием, и её можно найти фильтром «Устранена». VM таких строк не заводит
(пар десятки тысяч): пропавшая пара без решения следа не оставляет, у неё
нет истории «устранена». Assets — так же, как VM: расхождения считаются при
чтении и не хранятся, сравнить с прошлыми данными не с чем.

Assets: расхождения активов — находки области 0, подпись — «<актив>: <текст
расхождения>», тяжести нет. Подсчёты: в счётчики списка (`codes`,
`discrepancy_count`, фасет `code`) и обзора идут только расхождения с
учитываемым статусом, карточка показывает все со статусом. Объединение
активов переносит решения поглощённого актива на оставшийся
(`service.rekey`, событие `rekeyed`), если у того нет решения по тому же
ключу.

## Ограничения

- Решения привязаны к ключу. Смена формата ключа (новая версия анализатора
  AD/Антивируса, новая версия разбора SIEM) решения по старым находкам на
  новые не переносит.
- Ключ — до 400 символов.
- VM: ключ — `hostname|ip|cve`; при смене IP хоста или регистра его имени
  пара — новая находка.
- Assets: у расхождений нет возраста (`first_seen_at` пуст) — расхождения не
  хранятся, когда расхождение появилось впервые, неизвестно. Отвязка
  наблюдения решения на новый актив не переносит.
- SIEM: ключ подписан солью установки (`app_setting.siem_finding_key`), чтобы
  по ключу нельзя было восстановить значение находки. Соль должна пережить
  резервное копирование: дамп базы — целиком (`docs/install.md`, «Резервная
  копия»). Без соли при живых решениях STools новую не заводит, сверка
  пропускается, статусы SIEM показываются как «Новая».
- Просмотр не последнего снапшота: статусы — на сегодня (`is_latest: false`,
  `statuses_as_of: "today"`, предупреждение в интерфейсе).

## Подсчёты

Настройка `counted` — какие статусы входят в счётчики. По умолчанию не
учитываются `risk_accepted`, `false_positive`, `resolved`. От неё зависят
обзоры модулей, слой ATT&CK (AD, VM), «требует внимания» у правил SIEM.
Находка с неучитываемым статусом остаётся в списках со своим статусом.

## Списки модулей

Общие параметры списков находок AD, Антивируса, SIEM и VM:

| Параметр | Значение |
|---|---|
| `status` | коды через запятую или `all`; не задан — открытые (`new`, `in_work`, `fixed`, `reopened`); не задан при `risk_expiring=true` — `risk_accepted` |
| `assignee` | `me`, `none` или логин |
| `overdue` | `true` — только просроченные |
| `risk_expiring` | `true` — принятый риск, срок которого истекает в ближайшие 30 дней |

Поля строки: `status`, `status_title`, `assignee`, `assignee_name`,
`due_date`, `overdue`, `risk_until`, `first_seen_at`, `age_days`. Фасеты:
`facets.status`, `facets.assignee`, `facets.flags.overdue`,
`facets.flags.risk_expiring`; каждый фасет считается без своего фильтра, а
флаги сроков — ещё и без фильтра статуса: `risk_expiring` — среди принятых,
`overdue` — среди открытых, какой бы статус ни был выбран. Щелчок по флагу в
интерфейсе переключает список так, чтобы он показал то же, что счётчик.

Assets: строка списка — актив, а не находка, поэтому параметры — про его
расхождения: `disc_status` (вместо `status`; по умолчанию — учитываемые
статусы, а не открытые), `assignee`, `overdue`; актив подходит, если у него
есть такое расхождение (`docs/assets/api.md`).

## API

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/api/findings/state?module=&scope_id=&key=` | состояние и история одной находки; без строки — `new` и пустые поля |
| PUT | `/api/findings/state` | `{module, scope_id, key, status?, assignee?, due_date?, risk_until?, comment?}`; поле не передано — не трогается, `null` — очистить |
| POST | `/api/findings/comment` | комментарий без смены статуса |
| POST | `/api/findings/bulk` | `{module, scope_id, keys: [...] (≤ 5000) \| filter: {...}, change: {...}}` → `{changed}`; по фильтру у VM — 202 `{job_id}` (фоновая задача) |
| GET | `/api/findings/mine?status=&module=` | находки всех модулей, где исполнитель — я; сначала просроченные, затем по сроку и тяжести; по умолчанию открытые |
| GET | `/api/findings/mine/count` | `{open, overdue}` — для значка меню |
| GET | `/api/findings/summary?module=&scope_id=` | по статусам, просроченные, «риск истекает ≤ 30 дней», без исполнителя |
| GET | `/api/users/directory` | `[{login, display_name}]` — активные аналитики и администраторы; кому можно назначить |
| GET / PUT | `/api/settings/findings` | `{counted, risk_max_days, risk_accept_role}`; читают все, меняет администратор |

Строка «Моих находок»: `module`, `module_title`, `scope_id`, `key`, `title`,
`severity`, `status`, `status_title`, `due_date`, `overdue`, `risk_until`,
`present`, `first_seen_at`, `updated_at`, `link` (путь карточки в модуле).
Подпись SIEM — правило, класс и поле, без значения находки.

Права: чтение — все роли; запись в `/api/findings` — аналитик и
администратор; `risk_accepted` — по настройке `risk_accept_role`
(`analyst` — аналитик и администратор, `admin` — только администратор);
исполнитель — только из справочника. Смены пишутся в журнал действий с
кратким описанием (модуль, число находок, что изменено); массовые — ещё с
`bulk_id` событий и фильтром, если выбор был по фильтру.

## Настройки

Раздел «Настройки → Статусы находок» (`/settings/findings`): видят все,
меняет администратор.

- «Учитывать в подсчётах» — флажок на каждый статус (`counted`).
- «Максимальный срок принятия риска, дней» (`risk_max_days`): пусто — не
  ограничен; задан — «Принят риск» требует дату окончания не дальше срока.
- «Кто может принимать риск» (`risk_accept_role`).

## Перенос прежних вердиктов

Миграции 02.10.2026 перенесли прежние решения в `platform_finding_state` с
событием `migrated`:

- AD и Антивирус: «принята» → `risk_accepted` (обоснование, автор, дата).
- SIEM: «в работе» → `in_work`, «принята» → `risk_accepted`; только вердикты
  по uuid правила (по имени вердикты в коде не использовались и остались в
  архиве).

Старые таблицы переименованы, не удалены: `ad_verdict_archive_20261002`,
`ksc_verdict_archive_20261002`, `finding_verdict_archive_20261002`.
`downgrade` возвращает их и убирает перенесённые строки. Возраст
перенесённых находок заполняется при первой сверке.

## Разработчику

**Меняете логику находок или формат ключа — поднимайте версию:**
`ANALYZER_VERSION` (AD, Антивирус) или `kbaudit.__version__` (SIEM). Защита
от ложных «устранена» держится на ней: снапшоты разных версий не
сравниваются, и тысячи находок не закрываются разом из-за того, что у них
сменились ключи. Без новой версии сверка примет новые ключи за новые находки,
а старые — за устранённые.

Новый модуль подключается так: адаптер (`FindingAdapter` в
`api/platform/findings/adapters.py`: `scopes`, `has_scope`, `current` — `None`,
если данных нет, `first_seen_many`, `first_seen`, `link`),
`register_adapter` при импорте пакета модуля, `safe_reconcile` после commit
своих данных.

Модулю, у которого находок сотни тысяч (VM), есть необязательные методы
адаптера. `count_current(db, scope_id)` — число находок (`None` — данных нет)
и `present_keys(db, scope_id, keys)` — какие из ключей есть в данных: с ними
сверка идёт по строкам состояния кусками и все находки в память не
собирает, а `/api/findings/summary` их не перечисляет. `describe(db,
scope_id, keys)` — подписи (`title`, `severity`) пачкой: сверка обновляет их
только у строк, которые меняет, у строк с исполнителем и у неподписанных.
`on_states_created(db, states)` — новые строки области уже записаны (flush),
модуль может завести к ним свои данные в той же транзакции (VM —
`vm_finding_state_ref`, по которой список присоединяет статусы).

Массовая смена по фильтру фоновой задачей (`register_bulk_job`): нельзя
сейчас — `BulkConflict`, платформа отвечает 409.
