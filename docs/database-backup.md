# Резервное копирование и восстановление БД STools

`ops/stools_db.py` создаёт полный логический дамп **одной PostgreSQL-БД STools**, проверяет копию и восстанавливает её. Нужны Python 3.10+, Docker CLI и работающий контейнер PostgreSQL. `pg_dump`, `pg_restore`, `psql` и `createdb` берутся из этого контейнера; устанавливать PostgreSQL на Mac или сервер не требуется.

Копия содержит все схемы, таблицы, данные, последовательности, функции и large objects — без отбора модулей. В частности, сохраняются настройки, пользователи, решения аналитиков и `app_setting.siem_finding_key`. Это **не обезличенный диагностический пакет**: копия содержит конфиденциальные данные и должна оставаться в защищённом хранилище.

## Что сохранять вместе с БД

Дамп не содержит файлы из `/data` API: исходные выгрузки, кэши разбора и другие файлы, на которые ссылается БД. Для аварийного восстановления всего STools нужны также:

- согласованная копия **всего `/data` API**, не только вложенной папки с архивами;
- исходный `STOOLS_SESSION_SECRET` и используемые предыдущие ключи при ротации — в отдельном защищённом хранилище; без них сохранённые пароли и API-ключи не расшифровать;
- конфигурация установки и точная версия образов STools;
- отдельная копия хранилища коллектора, если требуется восстановить его собственные данные. Коллектор использует SQLite и не входит в PostgreSQL-дамп.

Роли и tablespaces всего PostgreSQL-кластера не экспортируются. При восстановлении владельцем объектов становится `POSTGRES_USER` выбранного контейнера, исходные SQL-grants/owners не применяются, используется стандартный tablespace. Это соответствует штатной конфигурации STools с одной DB-учёткой. Нестандартные DB-роли, права, per-database/per-role настройки сервера и расширения, требующие дополнительных пакетов, переносите отдельно. Используйте ту же версию образа PostgreSQL и STools; скрипт требует совпадения основной версии PostgreSQL и сохраняет encoding/locale исходной БД. Проверено на PostgreSQL 16.

## Создание копии

Команды выполняются из корня проекта. По умолчанию выбран контейнер `stools-db-1`, имя базы берётся из его `POSTGRES_DB`, пользователь — из `POSTGRES_USER`. Пароль используется внутри контейнера и не передаётся в аргументах команды на хосте.

```bash
STOOLS_BACKUP_DIR="$HOME/stools-backups/db-$(date -u +%Y%m%dT%H%M%SZ)"
python3 ops/stools_db.py backup "$STOOLS_BACKUP_DIR" --container stools-db-1
```

Для другого имени базы:

```bash
python3 ops/stools_db.py backup "$STOOLS_BACKUP_DIR" \
  --container stools-db-1 --database kbaudit
```

Запускайте **один** из примеров: каталог должен быть новым. Скрипт никогда не перезаписывает уже существующую копию. `docker context show` помогает проверить, к какому Docker-хосту обращается CLI.

Результат — каталог с правами `700` и двумя файлами с правами `600`:

| Файл | Содержание |
|---|---|
| `database.dump` | Сжатый PostgreSQL custom archive (`pg_dump -Fc`) |
| `manifest.json` | Формат копии, дата UTC, параметры БД, версия PostgreSQL, размер и SHA-256 дампа |

Дамп записывается сначала во временный файл. После полного чтения архива через `pg_restore` публикуются итоговые файлы; `manifest.json` появляется последним. При ошибке команда возвращает ненулевой код, неполный каталог остаётся для диагностики и не считается готовой копией. Не переименовывайте `.partial` в готовый дамп вручную: создайте копию заново в другом каталоге.

`pg_dump` получает согласованный снимок БД и может выполняться при работающем API. Для согласованной копии **БД вместе с `/data`** дождитесь окончания активных заданий, остановите приложения-писатели, затем снимите обе копии до их повторного запуска.

Пример для prod compose:

```bash
docker compose -f ops/docker-compose.prod.yml stop web api document-converter
python3 ops/stools_db.py backup "$STOOLS_BACKUP_DIR" --container stools-db-1
```

Для стенда используйте его фактические compose-файлы, в том числе overrides, если они применялись при запуске. Контейнер `db` должен оставаться работающим. Скрипт сам не останавливает и не запускает приложения.

Файлы `/data` можно сохранить из остановленного API без различий между named volume на Mac и bind mount на Linux:

```bash
set -o pipefail
umask 077
docker cp stools-api-1:/data/. - | gzip > "$STOOLS_BACKUP_DIR/api-data.tar.gz"
gzip -t "$STOOLS_BACKUP_DIR/api-data.tar.gz"
docker inspect --format '{{.Config.Image}}' stools-api-1 > "$STOOLS_BACKUP_DIR/stools-api-image.txt"
```

Этот дополнительный tar не включён в `manifest.json`: команда `verify` ниже проверяет только PostgreSQL-дамп. Сохраните также версии остальных сервисов, если они отличаются. После успешного копирования можно запустить ранее остановленные сервисы (`docker compose ... start document-converter api web`). Если копирование завершилось ошибкой, не считайте набор готовой резервной копией.

## Проверка копии

```bash
python3 ops/stools_db.py verify "$STOOLS_BACKUP_DIR" --container stools-db-1
```

Проверяются структура manifest, размер, SHA-256 и полный разбор/распаковка дампа. БД при этом не изменяется. Успех выводится как `"status": "verified"`, код завершения — `0`.

Контрольная сумма выявляет повреждение, но **не подтверждает доверенность источника**. Восстановление дампа исполняет SQL; используйте только собственные доверенные копии. Скрипт не шифрует файлы. При переносе вне защищённого хранилища применяйте утверждённое шифрование. Сжатый custom archive переносим между ARM и x86 при совместимых PostgreSQL/расширениях.

Периодически выполняйте настоящее пробное восстановление в отдельную БД или отдельный контейнер: `verify` не заменяет такую проверку.

## Восстановление

1. Подготовьте PostgreSQL той же основной версии, с нужными расширениями и совместимыми locale. Предпочтителен тот же образ PostgreSQL. Для восстановления используется DB-администратор контейнера, которому доступны `CREATE DATABASE` и переименование БД.
2. Сохраните актуальную копию перед восстановлением. Убедитесь, что хватает места на **старую и новую БД, дамп и WAL**. Предыдущая БД останется на диске после успешного переключения.
3. Остановите API и другие приложения/SQL-клиенты, подключённые к целевой БД. Для согласованного восстановления файлов остановите и конвертер. Не запускайте несколько восстановлений одной БД одновременно.
4. Проверьте Docker context, имя контейнера и целевой БД. Запустите:

```bash
python3 ops/stools_db.py restore "$STOOLS_BACKUP_DIR" \
  --container stools-db-1 \
  --database kbaudit \
  --confirm-database kbaudit
```

Для `restore` контейнер и подтверждение имени задаются явно. Системные `postgres`, `template0`, `template1` заменять нельзя. Допускаются ASCII-имена БД длиной до 63 символов: буквы, цифры, `_`, `.`, `-`, без дефиса в начале.

Скрипт проверяет копию, создаёт `stools_restore_<UTC>_<суффикс>` из пустого `template0` и загружает туда весь дамп в одной транзакции. Целевая БД до окончания загрузки не меняется. Затем в одной транзакции:

- прежняя БД переименовывается в `stools_before_<UTC>_<суффикс>`, подключения к ней запрещаются;
- восстановленная БД получает целевое имя.

Поэтому лишние таблицы и данные, появившиеся после резервной копии, **не смешиваются** с восстановленными. Они остаются в прежней БД для возможного отката. Если целевой БД не было, создаётся только восстановленная.

При ошибке импорта/проверки исходная БД сохраняется. Временная БД может остаться; её имя выводится в stderr. При обрыве связи во время переключения или прерывании команды сначала проверьте фактические имена БД — ответ мог потеряться уже после commit. Скрипт не удаляет базы автоматически и не запускает API. Содержимое SQL-ошибок скрывается, поскольку PostgreSQL может включать в них строки с конфиденциальными данными.

В успешном результате поле `previous_database` содержит имя прежней базы. Сохраните его. Затем:

1. При аварийном восстановлении на новом диске восстановите сохранённое содержимое `/data` в **пустой** каталог/том API; при возврате файлов на существующей установке предварительно сохраните прежний каталог/том. Простое наложение tar на текущие файлы не гарантирует согласованности.
2. Используйте исходный `STOOLS_SESSION_SECRET` и ту же версию образов STools. Для уже подготовленного пустого `/data` остановленного API можно распаковать копию с сохранением владельцев:

```bash
set -o pipefail
gzip -dc "$STOOLS_BACKUP_DIR/api-data.tar.gz" | docker cp -a - stools-api-1:/data/
```

3. Запустите конвертер/API/web выбранными compose-файлами. Старт API применяет миграции; поэтому сначала восстановите исходную версию, а обновление выполняйте отдельным шагом.
4. Проверьте вход, настройки подключений, досье, снимки AD/KSC/VM, находки и задания. Возвращаются также пользователи, права и расписания на момент копии; учитывайте это перед запуском восстановленной системы.
5. Прежнюю БД и сохранённые файлы удаляйте вручную только после проверки и окончания принятого срока отката. Повторные восстановления увеличивают занимаемое место.

## Откат неудачной проверки восстановленной системы

Остановите API и другие подключения. Подставьте `previous_database` из результата восстановления. Пример оставляет и неудачно восстановленную БД для разбора:

```bash
STOOLS_OLD_DB='stools_before_YYYYMMDDTHHMMSSZ_XXXXXXXX'
STOOLS_FAILED_DB="stools_failed_$(date -u +%Y%m%dT%H%M%SZ)"
docker exec -i stools-db-1 sh -ec '
  export PGPASSWORD="${POSTGRES_PASSWORD:-}"
  exec psql -X -q -v ON_ERROR_STOP=1 -U "${POSTGRES_USER:-postgres}" -d postgres \
    -v old_db="$1" -v current_db="$2" -v failed_db="$3"
' stools-rollback "$STOOLS_OLD_DB" kbaudit "$STOOLS_FAILED_DB" <<'SQL'
BEGIN;
SET LOCAL lock_timeout = '10s';
ALTER DATABASE :"current_db" ALLOW_CONNECTIONS false;
ALTER DATABASE :"current_db" RENAME TO :"failed_db";
ALTER DATABASE :"old_db" RENAME TO :"current_db";
ALTER DATABASE :"current_db" ALLOW_CONNECTIONS true;
COMMIT;
SQL
```

Верните соответствующие прежние файлы `/data`, ключ и версию STools, затем запускайте приложения. Команды отката не заменяют восстановление файлов и ключа.

## Проверки самого скрипта

```bash
python3 -m unittest discover -s ops/tests -p test_stools_db.py
STOOLS_TEST_DOCKER=1 python3 -m unittest discover -s ops/tests -p test_stools_db.py
```

Вторая команда поднимает собственный временный `postgres:16-alpine` без внешней сети и без общих томов/портов, затем удаляет только этот тестовый контейнер. Проверяются восстановление данных/sequence/функций/large objects, отсутствие смешивания с прежней БД и отказы при повреждённой копии, неверном подтверждении, несовпадении версии, активных подключениях и SQL-ошибке импорта.

Свойства формата и восстановления: [PostgreSQL pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html), [ALTER DATABASE](https://www.postgresql.org/docs/16/sql-alterdatabase.html).
